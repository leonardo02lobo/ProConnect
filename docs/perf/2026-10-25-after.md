## Planes de ejecución (tarea 6.2)

`perf/results/after-explain.txt` (`perf/bench/explain.sh after explain-after.sql`):

- **Q1 feed, 1.ª página**: `Index scan on p using idx_posts_feed (reverse)`, 21 filas, sin filesort; `user` por PK.
- **Q1 página profunda** con `created_at < :ts OR (created_at = :ts AND id < :id)`:
  `Index range scan on p using idx_posts_feed … (reverse)`, 21 filas leídas, 0,12 ms.
  La alternativa con comparación de tuplas `(created_at, id) < (:ts, :id)` **no** usa el rango: recorre 5.022

- **Q3 preview**: `Index range scan on c using idx_comments_post_feed` para los 20 posts + `Window aggregate`

- **Perfil**: `Index lookup on p using idx_posts_author_feed (user_id=…) (reverse)`.
- **Comentarios paginados**: `Index lookup on c using idx_comments_post_feed (post_id=…)`.

## Observaciones y riesgos

- **Like bajo contención**: con 10 VUs dando like/unlike **al mismo post**, el p50 sube de 6 ms (`after-v2`) a 31 ms
  y el rendimiento de 1.121 a 274 it/s: el `UPDATE posts SET like_count = like_count + 1` serializa las transacciones
  sobre la fila del post (es el coste de D5). Sigue por debajo de la línea base (p95 48 ms vs 81 ms) y es el peor caso
  (un único post caliente). Si un post viral lo necesitara: contadores por *shards* o agregación asíncrona.
- **Sentencias no DML**: cada petición añade 5 sentencias de control de transacción (`SET autocommit`,
  `SET SESSION TRANSACTION READ ONLY/WRITE`, `COMMIT`); el feed hace 8 en total (antes 10.006).
- **Comentarios**: pasa de 2 a 1 sentencia (ya no comprueba el post salvo en una página vacía).
- El rendimiento con un dataset 10× mayor no se ha medido; los planes son por índice y `LIMIT`, así que el coste
  por página no depende del tamaño de `posts`/`comments` (salvo el tamaño de los índices en memoria).
